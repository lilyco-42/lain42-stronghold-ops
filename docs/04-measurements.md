# 04 · 本地基准测试：策略 / 传输协议 / 语言的影响

**方法**：先抓**真实**数据，不是合成数据。用 Playwright 抓线上 86 条 `m.public` 帧
（占全部流量的 **85%**，中位 3624 字节），再拿它们跑各方案。
**每个方案都做正确性校验**（解出来必须和原帧逐字段一致）—— 会丢数据的方案不能用。

复现：

```bash
node capture-ws-frames.mjs              # 抓真实帧 → ws-frames.json
node bench-encoding.mjs                 # Node 侧全矩阵（含正确性校验）
cd bench-rust && cargo run --release    # Rust 侧对照
python3 delta-potential.py              # 增量潜力单独分析
```

---

## ① 编码策略 —— 收益最大

| 方案 | 86 帧合计 | 省 | 编码ms | 解码ms |
|---|---|---|---|---|
| JSON（基线） | 266.4 KB | 0% | 2.0 | 4.5 |
| **JSON + deflate(1)**（已上线） | **79.4 KB** | **70.2%** | 5.8 | 4.8 |
| JSON + deflate(6) | 75.6 KB | 71.6% | 5.4 | 4.6 |
| JSON + brotli(5) | 70.8 KB | 73.4% | **33.7** | 4.9 |
| MessagePack（裸） | 206.5 KB | 22.5% | 6.8 | 9.4 |
| MessagePack + deflate(1) | 78.3 KB | 70.6% | 5.8 | 5.9 |
| CBOR + deflate(1) | 76.0 KB | 71.5% | 5.2 | 6.2 |
| 增量 JSON | 116.6 KB | 56.2% | 2.3 | 3.0 |
| **增量 JSON + deflate(1)** | **33.3 KB** | **87.5%** | 4.1 | 3.9 |
| **增量 MessagePack + deflate(1)** | **32.4 KB** | **87.8%** | 6.6 | 4.8 |

**结论**：

1. **deflate 是主力**（70%）
2. **二进制格式本身几乎没用** —— msgpack 裸格式只省 22.5%，加 deflate 后 70.6%
   ≈ JSON+deflate 的 70.2% → **换 msgpack / CBOR / protobuf 收益 ≈ 0**
3. **增量是第二级杠杆**：**87.5%**，在现有基础上再降 **58%**
4. brotli 只多省 3.2%，**编码 CPU 贵 6 倍** → 在 2 核机器上不值

### 为什么二进制格式没用

deflate 已经消除了最大的冗余 —— **重复的 key**。剩下的内容（枚举值、ID、数字）
二进制编码省不了多少，而 msgpack 的整数变长编码反而**不如 JSON 文本对 deflate 友好**。

### 增量的两个前提（重要）

1. **必须处理 key 删除** —— `draft` 和 `unite` 这两个 key 会消失。不处理的话
   apply 会留着旧值 → 客户端**永久错位**。
2. **必须有 keyframe** —— 断线重连后要发一次全量，否则新客户端没有基线。

### 顺带：`serverNow` 在拖累压缩

每帧都变的毫秒时间戳（13 位高熵数字），100% 的帧都在变。
它可以改成增量（或让客户端用 RTT 自己算），这属于增量方案的一部分。

## ② 传输协议 —— 影响 ≈ 0

| 项 | 开销 |
|---|---|
| WS 帧头 2–14 B/帧 | **0.19%** 总量 |
| permessage-deflate 尾 4 B/帧 | 0.13% |

**换 WebTransport / QUIC / SSE 对字节数几乎零影响。**
QUIC 的价值在**延迟**（无队头阻塞），不在带宽。

**但压缩的「位置」极其关键** —— permessage-deflate 是**每连接压缩**，
CPU 随玩家数线性增长。把压缩搬到应用层（压一次、广播 N 次）能降 ~N 倍 CPU。

## ③ 编程语言（Node 22 vs Rust 1.99，同一批数据）

| 方案 | Node 编码 | Rust 编码 | Node 解码 | Rust 解码 |
|---|---|---|---|---|
| JSON | 2.0 | **1.0** | 4.5 | **2.1** |
| JSON + deflate(1) | **5.8** | 7.9 | 4.8 | **3.8** |
| MessagePack | 6.8 | **1.0** | 9.4 | **2.4** |
| MessagePack + deflate(1) | 5.8 | **5.2** | 5.9 | **3.7** |

**结论**：

- **字节数完全一样**（266.4 = 266.4）→ **换语言不改变流量**
- 语言只影响 CPU，**约 2×**（序列化/解析那段）
- **deflate 环节 Rust 反而更慢**（7.9 vs 5.8）—— Node 的 zlib 是 C 实现，
  Rust 的 `flate2` 是纯 Rust（`miniz_oxide`）

---

## 总结：三个方向里只有「策略」值得动

| 方向 | 收益 | 值不值得 |
|---|---|---|
| **编码策略** | 二进制格式 ≈ 0；**增量 −58%** | ✅ 只有增量值得 |
| **传输协议** | ≈ 0（但**压缩位置**很关键） | ❌ |
| **编程语言** | 字节数不变，只给 2× CPU | ❌（除非 CPU 成瓶颈） |

**顺带回答一个常见问题：「要不要用 Rust 重写服务端？」**

不建议。三条硬证据：

1. **Rust 解决不了痛点** —— 瓶颈是带宽，不是 CPU（重写前 stronghold 只占 9.9% CPU）。
   重写**一个字节都省不下来**。
2. **`sim` 是前后端双跑的共享组件** —— `server/sim/` 48 文件 / **31043 行**（占服务端 68%），
   而客户端**也跑同一份**（`public/js/battle/runner.js:174` 默认 `loadSim = loadBrowserSim()`），
   代码注释明确写着两边要「fails identically on both sides」。
   服务端换 Rust、客户端仍是 JS → 两边必须**逐位一致**（浮点语义、RNG、迭代顺序）→ 极难；
   而且 JS 那份**必须留着**，等于**永久维护两套 31k 行 sim**。
3. **上游一天十几个 commit** → Rust fork 立刻落后，且永远无法合并上游。

如果真要验证：**最小化可行性实验** —— 用 Rust 实现 `server/sim/damage.js` 的伤害计算，
与 JS 版对同一输入做**逐位比对**。这一步都过不了，后面 31k 行就不用谈了。
