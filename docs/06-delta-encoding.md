# 06 · 增量编码：端到端验证（6/6 通过）

> **状态：方案已验证，尚未实现。** 实现要改游戏代码 + 重启（会丢进行中的对局）。

## 为什么值得做

| 方案 | 86 帧合计 | 省 |
|---|---|---|
| JSON（原始） | 266.4 KB | 0% |
| JSON + deflate(1)（**已上线**） | 79.4 KB | 70.2% |
| **增量 + deflate(1)** | **34.1 KB** | **87.2%** |

在现有基础上**再省 58%**。换算到线上：每玩家 450 B/s → **约 190 B/s**。

## 方案设计

### 帧格式（应用层信封，整体 deflate 一次）

```
{ seq, k: 1, p: <完整状态> }     ← keyframe
{ seq, p: <补丁> }                ← 增量
{ seq, n: 1 }                     ← 无变化
```

### 三条关键规则（**都是测试逼出来的**）

#### 规则 1：keyframe 必须**重置序列号**

客户端重连后 `seq` 归零，**不能**要求 `e.seq === expectSeq + 1`。
keyframe 无条件接受并采用它带来的 `seq`。

> 我第一版测试就栽在这 —— 重连后状态永远对不上。

#### 规则 2：服务端要**给缺基线的客户端单独发 keyframe**

新加入 / 重连的客户端没有基线，收增量没意义。服务端在广播时：

```
① 增量（diff + deflate 一次）→ 广播给所有有基线的客户端
② keyframe（只在有人缺基线时压一次）→ 只发给缺基线的人
```

keyframe 是**罕见事件**，多压一次的成本可忽略。

#### 规则 3：`deepDiff` 必须**显式声明被删掉的 key**

用 `$del: [keys]` 表示。不处理的话 `apply` 会留着旧值 → **客户端永久错位**。

实测 `m.public` 里 `draft` 和 `unite` 这两个 key **会消失**（1 次 / 2 次）——
不处理就一定出错。

## 测试结果（`scripts/test-delta-e2e.mjs`，真实 86 帧）

| # | 测试 | 结果 |
|---|---|---|
| 1 | 稳态 4 客户端 | ✓ 省 **87.2%**；4 客户端全部收敛；收到 86/86 帧；服务端 **0.22 ms/帧** |
| 2 | 第 30 帧**中途加入** | ✓ 靠 1 次 keyframe 恢复，状态一致 |
| 3 | **断线重连** | ✓ 重连后立刻一致；再收 29 帧增量后仍一致 |
| 4 | **丢帧检测** | ✓ 能检测 seq 不连续 → 请求 keyframe → 恢复 |
| 5 | **边界数据 19 项** | ✓ 19/19 |
| 6 | **服务端 CPU** | ✓ 应用层「压一次广播 4 次」比「每连接压一次」**快 2.67×** |

### 测试 5 覆盖的边界

key 消失 / key 出现 / `number→string` / `object→array` / `array→null` /
`null→object` / 空对象 / 空数组 / 数组元素变化 / 数组长度变化 / 嵌套删除 /
深层新增 / 顶层清空 / 布尔翻转 / `0` 与 `false` 互转 / 负数与极小浮点 /
中文字符串 / 5000 字超长字符串 / 数组含 null

> `undefined` 值**不适用** —— JSON 不支持 `undefined`，WS 收到的数据解析后不可能出现。

### 测试 6 说明

- **现状**：序列化全量一次 + **每连接各压一次**（permessage-deflate 的行为）
- **应用层**：diff 一次 + **压一次**，同一份字节广播给 N 个客户端
- 连续帧场景下**快 2.67×**（N=4 时理论上限接近 4×，差额来自 diff 与序列化的共享开销）

## 实现要点（如果要做）

### 必须做 capability 握手（向后兼容）

服务端**不能**直接改发二进制 —— 已经加载了旧客户端的玩家会直接崩。
客户端在 `hello` 里带上能力标志，服务端只对支持的客户端用新格式。

### 客户端要改的地方

`public/js/net.js` 的消息处理：识别二进制帧 → inflate → 判断 `k` → keyframe 直接替换 / 增量 apply。
另外要维护 `seq`，检测到不连续时发 keyframe 请求。

### ⚠️ 风险

- **有状态**：客户端一旦错位就是永久错位（不像丢一帧只卡一下）→ 所以 `seq` + keyframe 恢复机制**必须有**
- **两端要同时改**，且必须向后兼容
- **每次上游更新都要重新打补丁** —— 上游一天十几个 commit

## 结论

**方案本身是安全可行的**，所有生产边界都验证过。

**但是否值得做，取决于你的带宽还剩多少余量**：
- 现在（压缩后）456 人 ≈ 335 KB/s，上限 375 KB/s → **89% 利用率**
- 再省 58% → 约 140 KB/s → **37% 利用率**
- 如果玩家还会继续涨，这个改动能把「撞带宽墙」的时间点推后约 2.4 倍
